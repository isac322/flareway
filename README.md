# Flareway

Flareway is a Kubernetes operator for Cloudflare Tunnel, Access, WARP, and Gateway API with an Envoy data plane.

The `flareway.bhyoo.com/v1alpha1` API implements two complementary ownership models:

| Area | API |
|---|---|
| Gateway traffic | `GatewayClassConfig`, `CloudflareTunnel` in default `Gateway` mode, Gateway API `Gateway`/`HTTPRoute`, and GEP-713 `AccessApplication` |
| Direct cloudflared config | `CloudflareTunnel.spec.configuration.mode: Direct` with the complete ingress service union, full `originRequest`, and `warpRouting` |
| Access applications | Gateway-attached `AccessApplication` types `SelfHosted`, `SSH`, `VNC`, `RDP`, `MCP`, `ProxyEndpoint`; non-Gateway `AccessStandaloneApplication` types `SaaS`, `Bookmark`, `Infrastructure`, `AppLauncher`, `WARP`, `BISO`, `DashSSO`, `MCPPortal` |
| Access dependencies | `AccessPolicy`, `AccessGroup`, `IdentityProvider`, `AccessCustomPage`, `DevicePostureRule`, `DevicePostureIntegration`, `AccessInfrastructureTarget`, `ServiceToken` |
| Private networking | `VirtualNetwork`, typed `NetworkRoute`/`HostnameRoute` references to `CloudflareTunnel` or `WARPConnector`, device settings/profiles, Gateway policies/lists, and Zero Trust organization settings |

The 22 shipped CRD Kinds are `GatewayClassConfig`, `CloudflareAccount`, `CloudflareTunnel`, `AccessApplication`, `AccessStandaloneApplication`, `AccessPolicy`, `AccessGroup`, `IdentityProvider`, `AccessCustomPage`, `DevicePostureRule`, `DevicePostureIntegration`, `AccessInfrastructureTarget`, `ServiceToken`, `VirtualNetwork`, `NetworkRoute`, `HostnameRoute`, `WARPConnector`, `DeviceProfile`, `DeviceSettings`, `ZeroTrustOrganization`, `ZeroTrustGatewayPolicy`, and `ZeroTrustList`.

Enum spelling follows the generated CRD schema: lifecycle and discriminator values are generally PascalCase, while a few wire-native Gateway, list, and device-profile values retain Cloudflare's spelling. Access application resources require `spec.accountRef`, immutable `spec.type`, and exactly one matching variant. `AccessApplication` derives public destinations from typed Gateway API targets; `pathScope` narrows that attachment, while `destinations[]` adds private, MCP portal, and Worker variants. `originJWT.audienceScope` selects the current application or every ready audience on the hostname.

Flareway never stores credentials in status. API tokens, identity-provider secrets, posture-integration credentials, SCIM credentials, service tokens, WARP Connector tokens, and create-only SaaS client secrets use Kubernetes Secret references or controller-owned Secrets.

Migration is explicit and fail-closed: observe an existing remote object with `managementPolicy: ObserveOnly` and `externalRef`, then use `AdoptById` plus expected attributes before Managed ownership. The same rule applies to generated bypass-child applications. Flareway trims the edges of `WARPConnector.spec.name` but compares the result case-sensitively; the name is not an adoption key. An existing exact-name connector or a case-only mismatch requires `externalRef.tunnelId`, `AdoptById`, and an exact non-empty `adoption.expect.name`. Interrupted WARP Connector creates recover only from a controller-owned status checkpoint that matches the remote identity and HA capability, never from user annotations. Tunnel configuration defaults to `Gateway`; `Direct` is an explicit whole-object ownership mode, so the two writers cannot overlap.

The generated CRDs in `config/crd/bases/` are the schema authority. See the [API reference](docs/api-reference.md), [design document](docs/design/001-cloudflare-gateway-api-integration.md), and [troubleshooting guide](docs/operations/troubleshooting.md).

Flareway remains experimental. Gateway API conformance and Cloudflare edge/WARP end-to-end evidence are reported separately; neither result substitutes for the other.
