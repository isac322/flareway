## 1. Envoy configuration validation

**Status: measured — passed unchanged**

### Goal

Validate `hack/envoy-reference.yaml` with Envoy `v1.39.1`. The plan preserved `admin.allow_paths` despite a compatibility uncertainty; the measured image accepted that field and the rest of the reference without changes.

### M0 command

```sh
mkdir -p hack/tls
openssl req -x509 -newkey rsa:2048 -nodes -days 1 \
  -subj /CN=private.example.internal \
  -keyout hack/tls/tls.key \
  -out hack/tls/tls.crt
docker run --rm \
  -v "$PWD/hack/envoy-reference.yaml:/etc/envoy/envoy.yaml:ro" \
  -v "$PWD/hack/tls:/etc/envoy/tls:ro" \
  envoyproxy/envoy:v1.39.1 \
  envoy --mode validate -c /etc/envoy/envoy.yaml
```

### Captured evidence

- Certificate creation exit code: `0`.
- Envoy validation exit code: `0`.
- Loaded resources: one static secret, four clusters, and three listeners.

```text
loading 1 static secret(s)
loading 4 cluster(s)
loading 3 listener(s)
configuration '/etc/envoy/envoy.yaml' OK
```

Envoy `v1.39.1` accepted the reference configuration unchanged, including `admin.allow_paths`. No compatibility diff was required.

## 2. Envoy idle footprint

**Status: measured**

### Goal

Measure the idle CPU and memory footprint of the production distroless Envoy image with one worker and hot restart disabled. Collect five `docker stats` samples and report the median CPU percentage and memory usage. Until measured, the deployment sizing remains the temporary `100m` CPU and `128Mi` memory request.

### M0 command

This measurement reuses the certificate generated by the validation command above.

```sh
docker rm -f flareway-envoy-idle 2>/dev/null || true
docker run -d --name flareway-envoy-idle \
  -v "$PWD/hack/envoy-reference.yaml:/etc/envoy/envoy.yaml:ro" \
  -v "$PWD/hack/tls:/etc/envoy/tls:ro" \
  envoyproxy/envoy:distroless-v1.39.1 \
  -c /etc/envoy/envoy.yaml \
  --concurrency 1 \
  --disable-hot-restart
sleep 10
for sample in 1 2 3 4 5; do
  printf 'sample=%s\t' "$sample"
  docker stats --no-stream --format '{{.CPUPerc}}\t{{.MemUsage}}' flareway-envoy-idle
  sleep 5
done
docker logs flareway-envoy-idle
docker rm -f flareway-envoy-idle
```

### Captured evidence

The measurement used the distroless image, a minimal valid static configuration, a 10-second warm-up, `--concurrency 1`, and `--disable-hot-restart`. The container remained running with exit code `0`.

| Sample | CPU | Memory |
|---:|---:|---:|
| 1 | `0.17%` | `17.34 MiB` |
| 2 | `0.15%` | `17.34 MiB` |
| 3 | `0.22%` | `17.34 MiB` |
| 4 | `0.24%` | `17.34 MiB` |
| 5 | `0.16%` | `17.34 MiB` |

- Median CPU: **`0.170%`**.
- Median memory: **`17.340 MiB`** (`18,182,308` bytes).

The measured idle memory is well below the provisional `128Mi` request. This local Docker Desktop `arm64` result is not, by itself, a Kubernetes production-sizing guarantee.

## 3. CoreDNS private-hostname resolution

**Status: measured — passed**

### Goal

Test the pod-local CoreDNS design from Appendix B. The measured behavior was:

- `admin.internal.example` resolved to `127.0.0.1`.
- `x.internal.example` resolved to `127.0.0.1`.
- `deep.x.internal.example` returned NXDOMAIN.
- `internal.example` returned NXDOMAIN.
- `google.com` resolved through `/etc/resolv.conf` forwarding.

The `hosts` plugin wildcard therefore matched one label and did not match deeper names or the apex.

### M0 command

```sh
mkdir -p /tmp/flareway-research/coredns
cat > /tmp/flareway-research/coredns/Corefile <<'EOF'
.:53 {
    bind 127.0.0.1
    hosts {
        127.0.0.1 admin.internal.example
        127.0.0.1 *.internal.example
        ttl 30
        no_reverse
        fallthrough
    }
    forward . /etc/resolv.conf
    reload 5s 2s
    errors
}
EOF

docker rm -f flareway-coredns 2>/dev/null || true
docker run -d --name flareway-coredns \
  -v /tmp/flareway-research/coredns/Corefile:/Corefile:ro \
  coredns/coredns:1.14.7 \
  -conf /Corefile
sleep 2

docker run --rm --network container:flareway-coredns busybox:1.37.0 \
  nslookup admin.internal.example 127.0.0.1
docker run --rm --network container:flareway-coredns busybox:1.37.0 \
  nslookup x.internal.example 127.0.0.1
docker run --rm --network container:flareway-coredns busybox:1.37.0 \
  nslookup deep.x.internal.example 127.0.0.1
docker run --rm --network container:flareway-coredns busybox:1.37.0 \
  nslookup internal.example 127.0.0.1
docker run --rm --network container:flareway-coredns busybox:1.37.0 \
  nslookup google.com 127.0.0.1

docker logs flareway-coredns
docker rm -f flareway-coredns
```

### Captured evidence

CoreDNS started successfully as `CoreDNS-1.14.7` on Linux `arm64`, listening on `127.0.0.1:53`. The measured container used the pinned digest and `NET_BIND_SERVICE` capability.

| Query | Exit | DNS result |
|---|---:|---|
| `admin.internal.example` | `0` | `NOERROR`; A `127.0.0.1` |
| `x.internal.example` | `0` | `NOERROR`; A `127.0.0.1` |
| `deep.x.internal.example` | `1` | `NXDOMAIN` |
| `internal.example` | `1` | `NXDOMAIN` |
| `google.com` | `0` | `NOERROR`; forwarding returned IPv4 and IPv6 addresses |

The planned Corefile produced the expected exact-host, one-label wildcard, deeper-name, apex, and forwarding behavior. No Corefile correction was required.

## 4. cloudflared runtime endpoints and flags

**Status: measured — passed**

### Goal

Start cloudflared `2026.9.1` with the documented fake tunnel token and inspect its local runtime endpoints before it has an active edge connection. Confirm the orchestration configuration metric name and the private DNS resolver flag.

### M0 command

```sh
FAKE_TOKEN="$(printf '%s' '{"a":"00000000000000000000000000000000","s":"AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=","t":"00000000-0000-0000-0000-000000000001"}' | base64 | tr -d '\n')"

docker rm -f flareway-cloudflared 2>/dev/null || true
docker run -d --name flareway-cloudflared -p 2000:2000 \
  cloudflare/cloudflared:2026.9.1 \
  tunnel --no-prechecks --metrics 0.0.0.0:2000 run --token "$FAKE_TOKEN"
sleep 5

curl -i http://127.0.0.1:2000/ready
curl -i http://127.0.0.1:2000/healthcheck
curl -i http://127.0.0.1:2000/config
curl -fsS http://127.0.0.1:2000/metrics \
  | grep '^cloudflared_orchestration_config_version'
docker run --rm cloudflare/cloudflared:2026.9.1 \
  tunnel run --help \
  | grep -- '--dns-resolver-addrs'

docker logs flareway-cloudflared
docker rm -f flareway-cloudflared
```

### Captured evidence

The fake token could not register a tunnel, as expected, but cloudflared continued serving its local observability endpoints.

```text
/ready       HTTP 503  {"status":503,"readyConnections":0,"connectorId":"<generated>"}
/healthcheck HTTP 200  OK
/config      HTTP 200  {"version":-1,"config":{"ingress":[{"hostname":"","path":null,"service":"http_status:503"...}
```

The metrics endpoint returned the exact metric metadata and initial sample:

```text
# HELP cloudflared_orchestration_config_version Configuration Version
# TYPE cloudflared_orchestration_config_version gauge
cloudflared_orchestration_config_version 0
```

The `/config` version and initial Prometheus gauge differ: `/config` reports `-1`, while `cloudflared_orchestration_config_version` reports `0`. The metric name is correct; consumers must not assume its initial value equals the `/config` version.

The help output contained:

```text
--dns-resolver-addrs value  Overrides the dynamic DNS resolver resolution to use these address:port's instead. (accepts multiple inputs) [$TUNNEL_DNS_RESOLVER_ADDRS]
```

The measured dynamic host port was `32768`. The expected log message was `Register tunnel error from server side error="Failed to get tunnel"`; it exposed no token.
