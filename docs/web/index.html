Executive Summary

핵심 설계 원칙 (12대 결정 요약)

오퍼레이터가 신뢰성, 표준 호환성, 엄격한 보안을 유지하기 위해 채택한 핵심 아키텍처 결정들입니다.

1. 데이터플레인: cloudflared + Envoy 동시 배치 Dual-Engine

cloudflared 네이티브 인그레스는 L7 기능(헤더/메서드/쿼리 매칭, 가중치 분할, URL 재작성, 리다이렉트)이 전무합니다. 따라서 cloudflared는 Edge 전송 및 per-ingress JWT 검증만 수행하고, Gateway API 표준 L7 라우팅은 같은 Pod 내 loopback으로 바인딩된 Envoy 프록시가 전담합니다.

2. 단일 소유자: 1 Gateway = 1 Tunnel Single-Writer

Cloudflare Tunnel 설정 API는 전체 문서 교체(whole-object PUT) 방식입니다. 여러 Gateway가 하나의 Tunnel을 공유하면 충돌이 불가피하므로, 하나의 Gateway가 정확히 하나의 Tunnel을 독점 소유하여 안전하고 결정론적인 조정을 보장합니다.

3. Zero-Annotation 철학 (GEP-713 정책 부착) Standard GEP-713

Gateway API 리소스(Gateway, HTTPRoute)에 Cloudflare 전용 비표준 어노테이션을 일체 읽지 않습니다. 인프라 바인딩은 parametersRef, 보안 정책은 타입 안전한 GEP-713 Direct Policy인 AccessApplication CRD를 통해 바인딩합니다.

4. Fail-Closed 보안 & Origin JWT 검증 강제 Zero Trust Origin

Edge의 Access 검사만 신뢰하지 않고, cloudflared 수신부에서 Cf-Access-Jwt-Assertion을 서명 검증합니다. 보호 대상 라우트의 AUD가 준비되지 않거나 Access 정책이 삭제되면 라우트는 자동으로 공개되는 것이 아니라 즉시 403 Forbidden으로 차단(Fail-Closed)됩니다.

High-Level Concept

개념 및 배경: 왜 Flareway가 필요한가?

클라우드플레어 네트워킹과 쿠버네티스 표준 인그레스 모델 간의 본질적인 기술 격차와 해결책을 설명합니다.

전통적인 Ingress/cfd의 한계와 L7 기능 격차 (The Capability Gap)

많은 개발자가 cloudflared를 쿠버네티스 인그레스로 직접 연결하려고 시도합니다. 그러나 공식 cloudflared의 인그레스 규칙 엔진은 단순한 호스트명과 비앵커(unanchored) Go 정규식 경로 매칭만을 제공합니다. 쿠버네티스 차세대 표준인 Gateway API (GatewayHTTP Core Profile)를 만족하기에는 아래와 같은 치명적인 한계가 존재합니다:

요구 기능 Gateway API (HTTPRoute) 요구 cloudflared 네이티브 인그레스 Flareway (Dual-Engine 해결책)
경로 매칭 Exact, PathPrefix, RegularExpression 비앵커 정규식만 지원 (오버랩 취약점 존재) 완전 지원 (Envoy)
헤더 / 메서드 매칭 HTTP Method (GET/POST 등), Header, QueryParam 미지원 완전 지원 (Envoy)
트래픽 분할 (Weight) 다중 백엔드 가중치 로드밸런싱 (Canary 90:10) 미지원 (단일 Service만 가능) 완전 지원 (Envoy Cluster)
URL 변환 및 필터 URLRewrite, RequestRedirect, RequestHeaderModifier 미지원 (요청 경로 원형 전달) 완전 지원 (Envoy Filter)
보안: Access JWT 검증 Edge 정책 통과 토큰의 오리진 내 암호학적 검증 HTTP 서비스에 한해 per-ingress 검증 지원 cloudflared 검증 + Envoy 연계

Specification & Standards

Gateway API 매핑 계약 & Conformance

쿠버네티스 Gateway API v1.6.2 표준 규격을 충실히 준수하며 비지원 필드를 처리하는 계약입니다.

Gateway 및 Listener 매핑 규칙

  • 1 Gateway : 1 Tunnel : Gateway.spec.infrastructure.parametersRef로 CloudflareTunnel CR을 바인딩합니다. 생략 시 동일 이름의 Tunnel이 자동 생성됩니다.
  • Hostname 필수 : Edge 및 WARP 라우팅 특성상 리스너의 hostname 지정은 필수입니다 (생략 시 Accepted=False/UnsupportedValue).
  • Public TLS 모드 : Public 리스너는 Cloudflare Universal SSL이 Edge에서 종료되므로 tls.certificateRefs를 지정하면 안 됩니다 (지정 시 UnsupportedValue).
  • Private TLS 모드 : Private 리스너는 Envoy가 직접 TLS를 종료하므로 certificateRefs가 필수입니다.
  • 주소 공개 (status.addresses) : Public 리스너가 1개 이상 존재할 경우 [{type: Hostname, value: <tunnel-id>.cfargotunnel.com}]을 게시합니다.

표준 기능 지원 범위 (Conformance Profile)

기능 분류 상태 지원 항목
Core Features 완전 지원 HTTPRoute 경로/헤더 매칭, 가중치 분할, 리다이렉트, HeaderModifier
Extended (L7) 완전 지원 HostRewrite, PathRewrite, CORS, QueryParamMatching, MethodMatching
Extended (TLS) 완전 지원 BackendTLSPolicy (Upstream Pod TLS 검증 및 SAN 검사)
Experimental v1 미지원 HTTPRouteRetry, sessionPersistence (UnsupportedValue 처리)
Zero Trust Security

보안 불변식 & Fail-Closed 설계

운영자의 실수나 CRD 삭제 시에도 트래픽이 절대 무방비로 외부에 노출되지 않도록 하는 방어 체계입니다.

🚨 보안 핵심 불변식: 정책 삭제 ≠ 퍼블릭 전환

기존에 AccessApplication으로 보호되던 호스트명의 CRD가 삭제되더라도 라우트가 자동으로 퍼블릭으로 열리지 않습니다. 플랫폼 운영자가 CloudflareAccount.spec.grants[].unprotectedHostnames에 해당 호스트명을 명시적으로 등록하지 않은 한, cloudflared는 즉시 http_status:403 규칙을 적용하여 모든 외부 요청을 차단합니다.

Fail-Closed Ingress Edge + Origin

Access Application의 aud가 발급되기 전까지는 트래픽 포워딩을 시작하지 않습니다. AUD 변경 시에도 구/신 토큰 동시 허용 없이 block-first(403) 원칙을 적용합니다.

루프백 리스너 분리 Anti-Traversal

동일 호스트명에서 /admin(보호)과 /v1(공개)이 공존할 때, 공개 리스너에는 애초에 /admin 라우트가 존재하지 않습니다. 따라서 /v1/../admin 같은 경로 탐색 우회가 원천 차단됩니다.

플랫폼 승인 경계 (Grants) Multi-Tenancy

테넌트는 자신이 속한 네임스페이스에 할당된 grants 범위(호스트명 패턴, 존, 백엔드 네임스페이스) 내에서만 리소스를 선언할 수 있으며, 타 테넌트 자원을 침범할 수 없습니다.

CloudflareTunnel Namespaced

Gateway와 1:1로 결합되어 원격 터널 수명주기, cloudflared/Envoy Pod 배포, DNS 동기화 및 리스너 노출 경로를 관리합니다.

CloudflareTunnel YAML 스키마 요약
kind: CloudflareTunnel
metadata: {name: cc-lb, namespace: llm-proxy}
spec:
  accountRef: {name: runbear}
  dns: {mode: Managed}
  listeners:
    - {name: admin, exposure: Private}
    - {name: proxy, exposure: Public}
AccessApplication GEP-713 Direct

Gateway 또는 HTTPRoute에 부착되는 Zero Trust 접근 제어 정책. Cloudflare Access App 생성 및 AUD 자동 획득을 수행합니다.

AccessApplication YAML 스키마 요약
kind: AccessApplication
metadata: {name: cc-lb-admin}
spec:
  targetRefs:
    - {group: gateway.networking.k8s.io, kind: Gateway, name: cc-lb, sectionName: admin}
  application: {sessionDuration: 720h}
  policies: [{policyRef: {name: allow-developers-warp}}]
  originJWT: {mode: Required}
ServiceToken Namespaced

기계 대 기계(M2M) 인증을 위한 Access Service Token을 발급받고 시크릿으로 안전하게 클러스터에 주입합니다.

AccessPolicy (테넌트 참조) Namespaced

테넌트 자체 정책 정의 또는 플랫폼 네임스페이스의 표준 공유 정책(ObserveOnly)을 참조하여 재사용합니다.

CloudflareAccount Cluster-Scoped

클라우드플레어 계정 ID, API 토큰 시크릿 참조, 그리고 각 테넌트 네임스페이스의 호스트명 및 기능 허가권(grants)을 정의합니다.

GatewayClassConfig Cluster-Scoped

GatewayClass에서 참조하는 인프라 템플릿. 커넥터 이미지, 리소스 요청, Envoy 프록시 기본값, Conformance 모드를 설정합니다.

AccessGroup & IdentityProvider Platform Shared

Okta, Google Workspace, Azure AD 등의 IdP 연동과 개발자/운영자 Access 그룹을 클러스터 전역에서 관리합니다.

DevicePostureRule Platform Shared

WARP 클라이언트 연결 상태, 디스크 암호화, EDR(CrowdStrike 등) 검사를 요구하는 단말 보안 자세 규칙을 정의합니다.

DeviceProfile Single-Writer Aggregator

WARP 클라이언트의 Split Tunnel (Include/Exclude)과 Fallback Domains를 전체 목록 교체 API에 맞춰 결정론적으로 집계 및 관리합니다.

VirtualNetwork & NetworkRoute Private CIDRs

사설 네트워크 격리를 위한 VNet 정의 및 쿠버네티스 서비스 CIDR(예: 10.96.0.0/12)의 터널 사설 라우트를 등록합니다.

HostnameRoute Private Hostname (GA)

CIDR 없이 내부 사설 도메인(예: admin.cc-lb.internal)을 터널로 직접 라우팅하는 Cloudflare One의 신규 기능을 선언합니다.

ZeroTrustOrganization & DeviceSettings Singleton

계정 전역의 WARP 세션 타임아웃(720h), 인증 도메인(auth_domain), 게이트웨이 프록시 활성화 플래그를 관리합니다.

Design Discipline

Annotation 정책: 엄격한 Zero-Annotation

Gateway API 리소스에서 어노테이션 남용을 배제하고 정책 부착(Policy Attachment) 표준을 고수합니다.

어노테이션 배제 이유와 대안 매핑

쿠버네티스 업스트림 Gateway API 가이드라인은 보안 및 라우팅 정책을 어노테이션으로 처리하는 것을 명시적으로 금지합니다. 어노테이션은 스키마 검증이 불가능하고, RBAC 권한 분리가 어려우며, 오타 발생 시 조용히 실패(silent fail-open)하는 치명적인 보안 결함이 있습니다.

기존 오퍼레이터들의 어노테이션 방식 문제점 Flareway의 표준 대안
cfgate.io/tunnel-ref: my-tunnel 비표준 바인딩, 타임아웃/오타 시 묵시적 실패 Gateway.spec.infrastructure.parametersRef
cfgate.io/access-policy: allow-devs 문자열 나열로 세부 옵션 및 다중 정책 조합 불가 AccessApplication CRD (GEP-713 Direct Policy)
cfgate.io/origin-connect-timeout: 30s 어노테이션 비대화 (Sprawl) 표준 HTTPRoute.spec.rules[].timeouts 사용
cfgate.io/origin-ssl-verify: false 보안 정책 우회 위험 표준 BackendTLSPolicy로 mTLS / CA 명시
Production Blueprint

실전 적용 사례: Runbear cc-lb 아키텍처

실제 운영 환경의 cc-lb 서비스를 Flareway 모델로 완벽하게 선언한 실전 매니페스트 번들입니다.

cc-lb 통합 선언 (Gateway + HTTPRoutes + AccessApplication) Production Ready
manifests/cc-lb-flareway.yaml 
# 1. Gateway 선언 (1 Gateway = 1 Tunnel)
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: cc-lb
  namespace: llm-proxy
spec:
  gatewayClassName: flareway
  infrastructure:
    parametersRef:
      group: flareway.bhyoo.com
      kind: CloudflareTunnel
      name: cc-lb
  listeners:
    - name: admin
      protocol: HTTPS
      port: 443
      hostname: cc-lb.runbear.io
    - name: proxy
      protocol: HTTPS
      port: 443
      hostname: cc-lb-proxy.runbear.io
---
# 2. CloudflareTunnel 인프라 선언
apiVersion: flareway.bhyoo.com/v1alpha1
kind: CloudflareTunnel
metadata:
  name: cc-lb
  namespace: llm-proxy
spec:
  accountRef: {name: runbear}
  tunnel: {name: k8s-llm-proxy-cc-lb}
  dns: {mode: Managed}
  listeners:
    - {name: admin, exposure: Public}
    - {name: proxy, exposure: Public}
---
# 3. HTTPRoute (Admin - 9090 포트)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: cc-lb-admin
  namespace: llm-proxy
spec:
  parentRefs: [{name: cc-lb, sectionName: admin}]
  rules:
    - backendRefs: [{name: cc-lb, port: 9090}]
---
# 4. HTTPRoute (Proxy - 8080 포트, /v1 경로)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: cc-lb-proxy
  namespace: llm-proxy
spec:
  parentRefs: [{name: cc-lb, sectionName: proxy}]
  rules:
    - matches: [{path: {type: PathPrefix, value: /v1}}]
      timeouts: {request: 0s} # 스트리밍 활성화
      backendRefs: [{name: cc-lb, port: 8080}]
---
# 5. AccessApplication (Admin 보호 정책 및 Origin JWT 검증 강제)
apiVersion: flareway.bhyoo.com/v1alpha1
kind: AccessApplication
metadata:
  name: cc-lb-admin
  namespace: llm-proxy
spec:
  targetRefs:
    - {group: gateway.networking.k8s.io, kind: Gateway, name: cc-lb, sectionName: admin}
  application:
    name: runbear-operation-cc_lb
    sessionDuration: 720h
    allowAuthenticateViaWarp: true
  policies:
    - policyRef: {name: allow-developers-warp, namespace: flareway-system}
    - policyRef: {name: deny-everyone, namespace: flareway-system}
  originJWT:
    mode: Required
Testing Strategy

검증 및 Conformance 테스트 모델

업스트림 표준 Conformance Suite와 Cloudflare Edge 실망 E2E의 현실적인 2단계 검증 접근법입니다.

Phase 1: In-Cluster Conformance (공식 리포트)

공식 Gateway API 테스트 러너는 임의의 호스트(example.com 등)로 패킷을 쏘기 때문에 DNS 존 검증을 거치는 Cloudflare Edge를 통과할 수 없습니다. 따라서 conformanceMode: true로 설정하여 클러스터 내부에서 Envoy 포트로 직접 공식 GatewayHTTP Core 프로파일 테스트를 완수하고 공식 적합성 리포트를 제출합니다.

Phase 2: Cloudflare Edge E2E (실망 검증)

실제 Cloudflare 테스트 계정을 통해 실제 Anycast DNS 생성, Universal SSL 인증서 발급, Access Google SSO 로그인 및 차단 화면 검증, 비인가 요청에 대한 JWT 위조 방어, WARP 사설 도메인 해석과 720시간 세션 동작을 실측 검증합니다.
